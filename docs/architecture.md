# Архитектура

## Общая схема

Сеть раздаёт роутер площадки; ноутбук — такой же его клиент, как и телефоны, но
только он держит сервер. Телефоны — обычные браузеры без установки приложений.
Интернет не нужен ни одной стороне.

```
[телефон]  \                                    [ноутбук :3000]
[телефон]   >--- Wi-Fi ---> [роутер] <---------- Node + Express
[телефон]  /                                    data/state.json
```

Сервер отдаёт статику и JSON API, клиент раз в несколько секунд спрашивает своё
состояние. Никаких внешних сервисов, базы данных и этапа сборки: на площадке без
интернета любая внешняя зависимость в рантайме — это сломанная игра.

## Модули

```
server/
  index.js      HTTP: маршруты, авторизация по токенам, лист бейджей, вывод адресов и QR
  game.js       правила: контракты, выстрелы, защита, подсказки, очки, патроны
  emblems.js    атрибуты эмблем, отрисовка в SVG, тексты подсказок
  nicknames.js  подсказыватель никнеймов для тех, кому лень придумывать
  store.js      состояние игры и запись на диск
public/
  index.html    приложение игрока
  app.js        экраны, опрос сервера, действия
  styles.css    оформление (тёмная тема, mobile-first)
  admin.html    пульт ведущего
  admin.js      логика пульта
scripts/
  smoke.mjs     прогон всего сценария против запущенного сервера
  check-docs.mjs сверка документации с кодом
```

Границы ответственности жёсткие: `game.js` ничего не знает про HTTP (принимает
объекты игроков, бросает `GameError`), `index.js` не содержит правил (только
разбор запроса, вызов правила и сериализация ответа). Благодаря этому автотест
проверяет правила через настоящий API, а не в обход него.

## Состояние

Единственный объект в памяти процесса, который сбрасывается в `data/state.json`.

```
state
  adminToken        токен ведущего, генерируется при первом запуске
  config            настройки из таблицы в game-rules.md
  game              { status, startedAt }
  slots[]           бейджи: код, эмблема, кем занят, за кем зарезервирован
  players{}         по id: имя, никнейм, токен, хеш и соль PIN, выданный и
                    зарезервированный слот, цель, очки, патроны, подсказки, щит,
                    журнал, входящие, счётчик неудачных входов
  codes[]           коды за активности: очки, лимит использований, кем использован
  events[]          лента для пульта ведущего
  version           версия формата
```

Запись — с задержкой 200 мс и через временный файл с переименованием, чтобы
внезапное закрытие ноутбука не оставило половину JSON. При выходе по `SIGINT`
состояние пишется синхронно.

База данных не нужна: тридцать игроков — это несколько десятков килобайт, а
отсутствие СУБД делает проект переносимым (склонировал, `npm install`, запустил).
Обратная сторона — сервер должен быть один; горизонтально это не масштабируется,
и не должно.

**Версионирование.** Если формат менялся, старое сохранение при запуске уезжает в
архивный файл рядом, а игра начинается заново. Так сервер не падает на данных,
собранных под другими правилами.

## Главное правило: сервер не раскрывает связки

Клиенту никогда не уходит связка «никнейм ↔ имя ↔ эмблема». Игрок получает:

- **свою** эмблему (SVG и словесное описание) — сначала зарезервированную, после
  выдачи её же как выданную;
- список реальных имён с `id` — для выстрела и защиты;
- табло с никнеймами и очками;
- никнейм своей цели — без имени, без эмблемы, без `id`;
- собранные подсказки об эмблеме цели — как готовый текст, а не как атрибуты.

Чужие эмблемы в приложении не появляются вообще: только вживую на бейджах.
Поэтому открытая консоль браузера не помогает — связки в трафике нет, она
существует только в памяти сервера. Любая новая ручка API обязана это правило
сохранять, иначе игра теряет смысл.

Эмблемы рендерятся в SVG на сервере: клиент получает готовую картинку и не знает,
из каких атрибутов она собрана. Иначе по атрибутам можно было бы вычислить цель,
не выходя из приложения.

## Поток запроса

1. Телефон открывает `http://<ip>:3000/` — Express отдаёт статику из `public/`.
2. Игрок регистрируется, сервер возвращает токен, клиент кладёт его в
   `localStorage`.
3. Дальше каждый запрос несёт токен в заголовке `x-player-token`; `requirePlayer`
   находит игрока или отвечает 401 с кодом `no_session`.
4. Ошибки правил — это `GameError` со статусом и машинным кодом; клиент показывает
   текст пользователю как есть (тексты сразу на русском).

Токен ведущего живёт в URL пульта и уходит в `x-admin-token`. Сессий на сервере нет:
в локальной сети на один вечер этого достаточно, а открывать такой сервер в интернет
не стоит.

**PIN и второй вход.** Токен привязан к одному браузеру, поэтому у игрока есть
второй путь: `POST /api/login` с именем и PIN из четырёх цифр возвращает тот же
токен. PIN лежит в состоянии только как `scrypt`-хеш со своей солью на каждого
игрока, сравнение — через `timingSafeEqual`, в ответах API он не появляется нигде,
кроме сброса ведущим. Пять неверных попыток закрывают вход на пять минут: имена
участников публичны, поэтому без ограничения четыре цифры перебирались бы за вечер.

PIN не заменяет личную выдачу бейджа: он даёт вернуться в свой кабинет, а не право
считаться игроком. Подставную регистрацию отсекает ведущий, а не проверка PIN, см.
[0017](history/0017-pin-to-return-to-account.md).

## Опрос вместо постоянного соединения

Приложение спрашивает `/api/me` раз в 8 секунд, пока страница видима, и
дополнительно при возврате в неё. Таймеры патронов и кулдаунов тикают локально,
поэтому обратный отсчёт выглядит живым между опросами.

Игра идёт несколько дней, телефоны блокируются, уходят из зоны Wi-Fi и
возвращаются. Постоянное соединение в таких условиях — это бесконечные
переподключения и разряженные батареи при нулевом выигрыше: патрон приходит раз в
час, реагировать за миллисекунды не нужно. Тридцать клиентов с опросом раз в 8
секунд — это меньше четырёх запросов в секунду.

## Жизненный цикл бейджа

Бейджи существуют раньше игроков: ведущий создаёт слоты (эмблема + код) и печатает
лист.

```
создание слотов -> печать -> регистрация: сервер резервирует слот и
показывает эмблему игроку -> ведущий отдаёт бейдж и подтверждает выдачу -> игра
```

У слота три состояния: свободен, зарезервирован за игроком, выдан. Пока бейдж
только зарезервирован, игрок числится зарегистрированным, но в игре не участвует:
`activePlayers()` отбирает по выданному слоту, поэтому такой человек не попадает ни
в список имён, ни на табло, ни в кандидаты на цель.

Подтверждает выдачу ведущий, а не игрок — иначе можно было бы войти в игру, не
взяв бейдж, и остаться невидимым для охотников. Код при подтверждении можно
исправить: если ведущий отдал не зарезервированный бейдж, а другой, резерв
освобождается, а игрок получает фактический.

Сканировать бейдж не нужно никому, поэтому QR на нём нет: код нужен только
ведущему, чтобы найти бейдж в стопке.

## Клиент

Ванильные HTML, CSS и JavaScript, без сборки и без CDN. Приложение игрока — одна
страница с экранами (регистрация, привязка бейджа, игра) и четырьмя вкладками:
контракт, выстрел, защита, табло.

Отсутствие фреймворка здесь не аскетизм: этап сборки означал бы, что на
ноутбуке-хосте нужно уметь собирать фронтенд, а внешний CDN — что игра зависит от
интернета, которого на площадке нет.

## Проверка

```bash
node scripts/smoke.mjs    # весь сценарий против запущенного сервера
node scripts/check-docs.mjs  # документация не расходится с кодом
```

`smoke.mjs` проходит игру целиком: создание бейджей, регистрация с резервом
эмблемы, выдача бейджа ведущим (включая выдачу не того бейджа и все отказы), старт,
выстрелы, защита, коды, подсказки, поздний участник, кончившиеся бейджи и допечатку,
проверка воронки подсказок и распределения эмблем. Состояние при этом сбрасывается,
поэтому на живой игре его запускать нельзя.

`check-docs.mjs` сверяет документацию с кодом: все ли маршруты описаны в
[api.md](api.md), все ли настройки — в [game-rules.md](game-rules.md), не битые ли
ссылки между документами.
